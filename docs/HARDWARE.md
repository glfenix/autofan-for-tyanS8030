# Железо и BMC: что выяснено экспериментально

Всё ниже проверено на **TYAN S8030GM2NE** (P/N `5411T6180007`), BMC AMI MegaRAC на
AST2500, **прошивка 6.02**, `ipmitool 1.8.19` на хосте Proxmox. Это то, что
нельзя узнать из мануала и что ломает готовые решения.

## Плата и BMC

```
ipmitool -I open mc info     -> Tyan Computer Corporation, Product ID 8030 (0x1f5e),
                               Firmware 6.02, IPMI 2.0
ipmitool -I open mc selftest -> passed
```

Доступ локально через KCS: `ipmitool -I open -D /dev/ipmi0 ...`. Вариант
`-I system-interface` на `ipmitool 1.8.19` не работает (`Error loading interface
system-interface`) — везде нужен именно `open`.

## Датчики

Веера (тахометры):

| датчик | состояние |
|---|---|
| `CPU_FAN`, `SYS_FAN_1`, `SYS_FAN_2`, `SYS_FAN_3`, `SYS_FAN_4` | есть показания |
| `SYS_FAN_5` … `SYS_FAN_12` | `No Reading` (разъёмы не задействованы) |

Температуры: `CPU_Tctl_Value`, `CPU_MOSFET`, `DIMM_MOSFET_1`, `DIMM_MOSFET_2`,
`CPU_SOC_MOSFET`, `SYS_Air_Outlet`, `MB_Air_Inlet`, `M.2/M.3_NVMe_0`,
`M.2/M.3_NVMe_1`, а также восемь датчиков каналов памяти
`P0_UMC0_CH_A0` … `P0_UMC7_CH_F0`.

SDR обновляется раз в 1–2 с, поэтому опрос чаще 20 с смысла не имеет, а один
`ipmitool sdr elist` на цикл дешевле, чем отдельный вызов на каждый датчик
(демон кэширует SDR на цикл).

## Каналы ШИМ

| PWM | разъём |
|---|---|
| 0 | `CPU_FAN` |
| 1 | `CPU1_FAN` |
| 2 | `SYS_FAN_1` |
| 3 | `SYS_FAN_2` |
| 4 | `SYS_FAN_3` |
| 5 | `SYS_FAN_4` |

Соответствие PWM↔тахометр проверено поштучно: запись на `0x02` меняла обороты
`SYS_FAN_1`, и так далее до `0x05`.

## Команды управления вентиляторами

Прошивка 6.02 принимает **только** новый формат (профиль `tyan64`):

```bash
ipmitool -I open raw 0x2e 0x44 0xfd 0x19 0x00 <pwm> 0x01 <duty>   # ok, ответ "fd 19 00"
```

Что не работает:

```bash
ipmitool -I open raw 0x2e 0x05 0xfd 0x19 0x00 <pwm> <duty>
  -> rsp=0xc7 Request data length invalid     # старый формат (профиль tyan32) этим BMC отвергнут

ipmitool -I open raw 0x2e 0x44 0xfd 0x19 0x00 <pwm> 0x01 0xff
  -> rsp=0xcc                                 # возврата в автоматический режим программно нет
```

Важная деталь кодирования: байты данных надо передавать как `0x00`…`0x64`.
`ipmitool` понимает только десятичные числа без префикса либо числа с `0x`;
«шестнадцатеричное» `5a` он отвергает (`Given data "5a" is invalid.`), а голое
`40` читает как сорок в десятичной системе, а не как `0x40`. Отсюда обязательный
формат `0x%02x` во всех командах (есть регрессионный тест).

Ручной установленный duty BMC удерживает сам — проверено более 4 минут,
автоматика платы его не перебивает. Поскольку обратного хода нет, демон при
остановке ставит `ON_EXIT_DUTY`, а не «возвращает авто».

## Redfish — почему не использовали

* `/redfish/v1/Managers/Self/FanControls` → `Base.1.5.ResourceMissingAtURI`.
* `/redfish/v1/Chassis/Self/Thermal` существует и содержит `Fans` — но только
  чтение, управлять нельзя.
* `/redfish/v1/Chassis/Self/Power` отвечает `PowerConsumedWatts: 0`, а оба
  PSU в статусе `Absent`: телеметрия энергопотребления на этой плате
  недоступна, так что косвенно оценить нагрузку через BMC нельзя.

## Калибровка duty → обороты

Замерено на четырёх 120 мм вентиляторах этой сборки:

| duty | 35 | 45 | 55 | 60 | 75 | 85 |
|---|---|---|---|---|---|---|
| RPM | 828 | 966 | 1104 | 1242 | 1518 | 1656 |

Аппроксимация `RPM = 202 + 17.2 × duty` (`RPM_OFFSET`, `RPM_PER_DUTY`),
попадание ±3 %. Через ноль линия не проходит: на 20–30 % тахометр показывает
~690 RPM, то есть у зависимости есть смещение, и без него проверка результата
ругается на «слишком быстрые» вентиляторы на низких duty.

Отклик тахометра после смены duty — 7–10 с, поэтому `VERIFY_DELAY_SECONDS=15`.

## GPU в виртуальной машине

Карта (RTX 5080) проброшена в гостевую ВМ Proxmox, поэтому на хосте NVML её не
видит. Чтение идёт через qemu-guest-agent:

```bash
qm guest exec 104 -- /usr/bin/nvidia-smi \
    --query-gpu=index,temperature.gpu,memory.used,power.draw,clocks.sm,utilization.gpu \
    --format=csv,noheader,nounits
```

Что надо знать:

* Ответ `qm guest exec` — JSON, где `"exited"` — **число** (`1`), а не булево:
  жёсткая типизация вида `Exited bool` ломается на `json: cannot unmarshal number`.
* Если гостевой агент не отвечает (ВМ выключена или агент лежит), источник
  помечается `OPTIONAL=1` и не считается аварией: иначе ночной простой ВМ
  взвинтил бы вентиляторы до аварийных 85 %.
* `nvidia-smi` отвечает ~0.9 с — на цикл опроса 25 с это незначительно, но
  источник читается один раз за цикл, а не по разу на каждый датчик.
* `power.draw` из того же CSV — источник для упреждающей кривой (см.
  `docs/DESIGN.md`), отдельного вызова не требует.

## Топология, важна для трактовки датчиков

Хост: AMD EPYC 7443, 24 ядра / 48 потоков. ВМ 104 — 24 vCPU, то есть 100 %
нагрузки внутри ВМ — это только ~50 % логических процессоров хоста: тесты
нагрузки надо запускать на хосте, иначе цифры врут (см. `docs/RESULTS.md`).
