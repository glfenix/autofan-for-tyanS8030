# Алгоритм управления

Один цикл демона (`Controller.Step`) устроен так:

```
1. один вызов ipmitool sdr elist  -> кэш SDR на весь цикл
2. прочитать все источники         (gpu / bmc / hwmon), по одному разу
3. для каждой группы:
     отбросить источники ниже FLOOR и недоступные
     агрегировать оставшиеся (max | mean | min)
     duty_температуры = кривая(агрегат)
     duty_упреждения  = кривая_мощности(Вт GPU)
     цель = максимум из них, ограничен снизу стартовым, сверху максимумом
     решить, менять ли (гистерезис), и записать в BMC
4. проверить тахометры (если включено)
5. сохранить состояние
```

## Источники и пороги учёта (`FLOOR`)

Источник — это не датчик, а именованная величина: температура GPU (из ВМ или
локально), один или несколько BMC-датчиков с агрегатом, или группа hwmon-файлов.

`FLOOR` нужен потому, что на этой плате датчики DIMM/MOSFET тёплые сами по себе
(47–53 °C в простое). Без порога они не дали бы вентиляторам опуститься до
стартовых 35 %: «средний» датчик никогда не стал бы холодным. Источник ниже
своего порога не участвует в агрегате — как если бы его не было.

Классификация источника за это отвечает:

| случай | трактовка |
|---|---|
| источник ответил, температура ≥ `FLOOR` | участвует в агрегате |
| источник ответил, температура < `FLOOR` | «холодный», в агрегат не входит |
| источник ответил `0 °C` или меньше | **неисправность**, не температура |
| hwmon-путь ничего не нашёл | **неисправность** (не пустой результат) |
| ВМ с GPU выключена, `OPTIONAL=1` | отсутствие данных, но не авария |

Последние три строки — то, на чём готовое решение ломается: молчаливый ноль от
мёртвого датчика выглядит как «холодно» и укладывает вентиляторы в минимум.

## Агрегация

`AGG=max` (по умолчанию) — по максимальной температуре. Это правильная
консервативная стратегия для корпуса, где один горячий узел важнее средних
градусов. `mean`/`min` есть, но на этой машине не применяются.

## Кривая по температурам

Точки вида `ТЕМП:ПРОЦЕНТЫ`, сортируются и нормализуются автоматически. Режим
`step` (по умолчанию) держит значение до следующей точки, `linear` интерполирует.

```
45:35 50:45 60:55 70:70 78:85 85:100
```

Ниже 45 °C — стартовые 35 %, при 50 °C — 45 %, при 85 °C — максимум. Точки
подбираются под своё железо (см. `docs/TUNING.md`), проверка конфига не
позволяет точке выйти за `MIN_DUTY..MAX_DUTY`.

## Упреждение по мощности GPU

Температура ядра карты — плохой сигнал: её охлаждение справляется, карта
показывает 42–53 °C, тогда как в корпус уходит 110–300 Вт, и греются уже
датчики той зоны, куда направлен выхлоп. Мощность — это и есть тепловыделение,
поэтому она используется как **опережающая нижняя граница**:

```
G1_POWER_CURVE=80:40 150:50 220:60 300:75     # ВТ:ПРОЦЕНТЫ
итог = макс(кривая_температур, кривая_мощности)
```

Температура остаётся старшей: 85 °C уводят в 100 %, даже если ватты просят 40 %.
Вниз duty уходит по обычным правилам (шаг + выдержка), поэтому короткий всплеск
инференса не гоняет вентиляторы туда-сюда. Если карта перестанет греть зону
памяти/CPU (райзеры, другое шасси) — кривую можно оставить (она про ватты) или
обнулить пустой строкой.

## Гистерезис

* вверх — немедленно (без выдержки);
* вниз — только если изменение не меньше `STEP` **и** с прошлого изменения
  прошло `DWELL`.

Асимметрия сознательная: лишний шум лучше, чем недоохлаждение. За 15 минут
наблюдения с реальной нагрузкой это дало три перехода вместо десятка.

## Критический режим и отказ

* любой источник выше `CRITICAL_TEMP` (по умолчанию 80 °C) — группа немедленно
  уходит в `MAX_DUTY`, опрос ускоряется до `FAST_POLL_INTERVAL`;
* ни один источник не ответил — `FAILSAFE_DUTY` (85 %), **повышение немедленно,
  понижение никогда**; число подряд идущих неудачных циклов попадает в журнал;
* «все источники живые, но ниже порогов» — это холодная машина, а не авария:
  тогда `MIN_DUTY`. Различие этих двух случаев принципиально, на нём держится
  вся безопасность.

## Стартовое значение, состояние, остановка

* при запуске сервиса, до первого решения, группам придаётся `STARTUP_DUTY`
  (35 %). Это даёт предсказуемое поведение после загрузки ОС вместо наследия
  BIOS/предыдущей сессии;
* **стартовое значение не опускает**: если в `state.json` записано 85 %, рестарт
  сервиса не уложит их в 35 % — сначала измерение, потом решение;
* состояние (`/var/lib/autofan/state.json`) сохраняется только если хотя бы одна
  запись в BMC удалась — иначе восстановление показало бы то, чего нет;
* при SIGTERM ставится `ON_EXIT_DUTY`. После SIGKILL или падения BMC вентиляторы
  остаются на последнем duty — отсюда минимум 35 % и аварийные 85 %.

## Проверка результата

После смены duty демон ждёт `VERIFY_DELAY_SECONDS` (тахометр приходит в
соответствие за 7–10 с) и сверяет обороты с калибровкой
`RPM = RPM_OFFSET + RPM_PER_DUTY × duty`. Отклонение больше `RPM_WARN_FACTOR`
(30 %) — предупреждение в журнал. Это ловит мёртвый подшипник, оборванный
тахометр и вентилятор, подключённый не в тот разъём. Смещение обязательно: у
тахометров этой платы зависимость не проходит через ноль (35 % → 828 RPM).

## Производительность и побочные эффекты

Все обращения к BMC сериализованы мьютексом (KCS не переваривает параллельные
запросы), SDR кэшируется на цикл: восемь BMC-источников читаются одним вызовом
`ipmitool sdr elist`, а не восьмью. GPU читается один раз за цикл (~0.9 с через
qemu-guest-agent). При `POLL_INTERVAL=25` это один вызов SDR + один вызов гостя
на цикл, то есть нагрузка на BMC и на guest agent пренебрежимая.

## Перечитывание конфига

`SIGHUP` (`systemctl reload autofan`) пересобирает контроллер из нового конфига,
сохраняя текущий duty (он восстанавливается из `state.json`). Битый конфиг —
ошибка в журнал, работа по прежнему; сервис не перезапускается и вентиляторы не
трогаются.

## Как это перекрыто тестами

| тест | что доказывает |
|---|---|
| `TestStepCurvePoints`, `TestCurveStep`, `TestCurveLinear`, `TestUnsortedCurveIsSorted` | кривая, сортировка, режимы |
| `TestFloorSkipsColdSensor`, `TestAllColdIsNotFailsafe` | пороги источников, «холодная машина» ≠ авария |
| `TestZeroTempCountsAsNoData`, `TestHwmonMissingPathReturnsError` | ноль и пустой hwmon-путь — отказ, а не холод |
| `TestNoDataGoesToFailsafe`, `TestNoDataNeverLowers` | аварийный duty и запрет понижения без данных |
| `TestRaiseImmediateLowerAfterDwell` | гистерезис |
| `TestStartupAppliesStartupDuty`, `TestStartupKeepsHotDuty` | старт: ставит 35 %, но не опускает горячее |
| `TestCriticalForcesMaxAndFastPoll` | критический режим |
| `TestRPMCalibrationMatchesHardware` | калибровка тахометров соответствует замерам |
| `TestLoadVarsConfig`, `TestInlineCommentsAndQuotes`, `TestBadLineIsReported` | парсер `KEY=VALUE` |
| `TestRawCommandHexEncoding` | байты данных уходят как `0x%02x` |
